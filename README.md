# TilaPulse

TilaPulse is a prototype tilapia pond monitoring system. One physical ESP32 sends temperature, pH, and dissolved oxygen readings to a FastAPI backend. The Flutter app displays the latest reading, while the backend can run an LSTM and BOCPD risk pipeline over a sensor sequence.

## Project Flow

```text
ESP32
  -> POST /api/readings
  -> FastAPI validation, device-key authentication, and Philippine timestamp
  -> device-scoped SQLAlchemy storage
  -> Flutter connects with a device key and receives a bearer session token
  -> POST /api/devices/{device_id}/predict
  -> missing-value handling and normalization
  -> fixed-length sliding window
  -> unidirectional PyTorch LSTM probability
  -> BOCPD change-point probability
  -> weighted risk score
  -> Flutter app consumes the JSON response
```

The backend identifies devices by `device_id`. Devices must be registered by an administrator before they can submit readings. The database is selected with `DATABASE_URL` and supports SQLite for local development and PostgreSQL deployments. The Flutter app stores device session tokens in secure storage and selects from the devices connected to that app.

A reading contains:

- `device_id`
- `temperature`
- `ph`
- `dissolved_oxygen`
- `timestamp` generated by the backend

Reading ingestion requires the device's shared key in the `X-Device-Key` header. Flutter read and control routes require a bearer session token obtained from `/api/devices/connect`; sessions are device-scoped and can be revoked.

## Backend Routes

| Method | Route | Purpose |
| --- | --- | --- |
| `GET` | `/` | Basic API information |
| `GET` | `/api/health` | Health check |
| `POST` | `/api/admin/devices` | Register a device; requires `X-Admin-Key` and returns the raw key once |
| `GET` | `/api/devices` | List registered devices |
| `POST` | `/api/devices/connect` | Exchange a device ID/key for a bearer session token |
| `DELETE` | `/api/devices/disconnect` | Revoke the current bearer session |
| `GET` | `/api/devices/{device_id}/command` | Return the device reading state; requires `X-Device-Key` |
| `PATCH` | `/api/devices/{device_id}/reading-state` | Enable or pause readings for the authenticated device |
| `POST` | `/api/readings` | Validate and store one sensor reading; requires `X-Device-Key` |
| `GET` | `/api/readings?device_id=pond-1&limit=20` | Return readings for the authenticated device |
| `GET` | `/api/readings/latest?device_id=pond-1` | Return the latest reading for the authenticated device |
| `POST` | `/api/devices/{device_id}/predict` | Run and persist one LSTM + BOCPD risk assessment |
| `GET` | `/api/devices/{device_id}/risk/latest` | Return the latest persisted risk assessment |
| `GET` | `/api/devices/{device_id}/risk/history` | Return persisted risk assessments |
| `GET` | `/api/devices/{device_id}/alerts` | List active threshold alerts |
| `DELETE` | `/api/devices/{device_id}/alerts/{alert_id}` | Resolve an alert |
| `POST` | `/api/admin/devices/{device_id}/rotate-key` | Rotate a device key and revoke its sessions |

Device listing and mock-data API routes were intentionally removed.

## Running the Backend

From the `server` directory:

```bash
python -m venv .venv
```

Windows PowerShell:

```powershell
.venv\\Scripts\\Activate.ps1
pip install -r requirements.txt
python -m uvicorn app.main:app --reload
```

For an ESP32 on the same Wi-Fi network, bind the API to the computer's LAN interfaces:

```powershell
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

The API is then reachable from the computer at `http://localhost:8000` and from the ESP32 at `http://<computer-lan-ip>:8000`. Swagger UI is available at `/docs`, and the OpenAPI document is at `/openapi.json`.

For local development, copy `server/.env.example` to `server/.env` and set the database and admin credentials:

```env
DATABASE_URL=sqlite:///./tilapulse.db
ADMIN_API_KEY=replace-with-a-long-admin-secret
PREDICTION_ALPHA=0.7
PREDICTION_BETA=0.3
PREDICTION_WINDOW_SIZE=20
```

Run tests with:

```bash
python -m pytest -q
```

## Reading API

Submit a reading:

```bash
curl -X POST http://localhost:8000/api/readings \
  -H "Content-Type: application/json" \
  -H "X-Device-Key: replace-with-a-private-test-key" \
  -d '{
    "device_id": "pond-1",
    "temperature": 29.5,
    "ph": 7.2,
    "dissolved_oxygen": 5.8
  }'
```

Response:

```json
{
  "temperature": 29.5,
  "ph": 7.2,
  "dissolved_oxygen": 5.8,
  "timestamp": "2026-09-18 14:30:00"
}
```

The timestamp uses Philippine local time and the format `YYYY-MM-DD HH:MM:SS`.

## ESP32 Integration

Register the device through the admin route first. The raw device key is returned once and must be placed in `DEVICE_KEY` in `tilapulse_device.ino`. Set `API_URL` to the computer's LAN IP, not `localhost`, and set `DEVICE_ID` to the registered ID. Wi-Fi is provisioned through the WiFiManager setup access point rather than hardcoded credentials. The device sends one authenticated reading every two seconds to `POST /api/readings`.

The firmware currently implements ingestion only. It does not yet poll `/api/devices/{device_id}/command`, so the backend reading-enabled switch is not enforced on the ESP32.

Register and connect a device for local testing:

```bash
curl -X POST http://localhost:8000/api/admin/devices \
  -H "X-Admin-Key: replace-with-a-long-admin-secret" \
  -H "Content-Type: application/json" \
  -d '{"device_id":"pond-1","name":"Pond 1","device_key":"replace-with-a-private-device-key"}'

curl -X POST http://localhost:8000/api/devices/connect \
  -H "Content-Type: application/json" \
  -d '{"device_id":"pond-1","device_key":"replace-with-a-private-device-key"}'
```

Get the latest reading:

```bash
curl "http://localhost:8000/api/readings/latest?device_id=pond-1" \
  -H "Authorization: Bearer <token>"
```

Get recent history:

```bash
curl "http://localhost:8000/api/readings?device_id=pond-1&limit=20" \
  -H "Authorization: Bearer <token>"
```

## Prediction Pipeline

`POST /api/devices/{device_id}/predict` requires that device's bearer session, loads its persisted readings, runs one assessment, and stores the result. The preprocessor fills missing values using the previous available value, normalizes the three sensor features, and pads or trims the sequence to the configured window size. The default window size is 20.

The same normalized window is sent to both models:

- The unidirectional PyTorch LSTM returns `lstm_probability`.
- BOCPD processes each window row and returns `bocpd_change_point_probability` in the persisted API response.
- The final score is `0.7 * lstm_probability + 0.3 * bocpd_probability` internally by default. These weights are configurable through `prediction_alpha` and `prediction_beta`; the persisted response names the BOCPD value `bocpd_change_point_probability`.

Example request:

```bash
curl -X POST http://localhost:8000/api/devices/pond-1/predict \
  -H "Authorization: Bearer <token>"
```

Example response:

```json
{
  "lstm_probability": 0.72,
  "bocpd_change_point_probability": 0.61,
  "risk_score": 0.687,
  "risk_label": "high"
}
```

The endpoint returns HTTP 503 with training instructions if `models/lstm_model.pt` is unavailable.

## Synthetic Data and Training

Synthetic data is not an API feature and must not be treated as real disease evidence. `server/app/synthetic_data.py` generates reproducible labelled sequences representing:

- normal conditions
- gradual deterioration
- sudden changes
- recovery

Train the development checkpoint from the `server` directory:

```bash
python scripts/train_lstm.py
```

The script generates 200 sequences, preprocesses them into 20-step windows, trains the LSTM for 20 epochs, and writes `server/models/lstm_model.pt`. A real deployment requires an appropriately labelled farm dataset and proper evaluation; the synthetic checkpoint is only for software development.

## Flutter Integration

The Flutter HTTP client is in `client/lib/services/api_service.dart`. It connects devices, stores bearer tokens securely, and calls the authenticated reading, alert, device-control, and risk-assessment routes. The dashboard screens are under `client/lib/pages/`.

For local development:

- Flutter Web or desktop usually uses `http://localhost:8000`.
- The Android emulator uses `http://10.0.2.2:8000`.
- A physical phone should use the computer's LAN IP address.

The Flutter client fetches live readings, device-scoped predictions, alerts, and registered device metadata. If no ESP32 is connected yet, register a device and use the authenticated `POST /api/readings` curl command above to seed a test reading through the real ingestion path.
